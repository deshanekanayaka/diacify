Diacify Architecture · Part 1

How Diacify works, from the top down

A clinician records what they measured at a patient visit. Diacify answers with a diabetes risk assessment. Everything below explains how that sentence turns into a running system — no prior knowledge of this codebase assumed.

Part 1 · High level The shape of the system and the four ideas you need before any code makes sense. Readable start to finish in about ten minutes.
Part 2 · Low level One request traced end to end, the gates, RLS in detail, ML serving, the training pipeline, and the seams.
01

What Diacify is

Diacify is a tool for one kind of person doing one kind of job: a clinician, seeing a patient, who wants to know how that patient's numbers read against a diabetes risk model.

The whole product is three nouns and one verb: a clinician keeps patients, each patient accumulates visits, and recording a visit produces a risk assessment.

No appointments, no analytics dashboard. Both existed in legacy and were deliberately left out ADR-043.

One pass through the product

The clinician doesDiacify recordsThey get back
Signs up, signs in An identity in Supabase Auth A session; everything after this is scoped to them
Adds a patient with a chart reference A patients row: reference, sex A patient in their list — no name, no date of birth
Records a visit: age, blood pressure, BMI, HbA1c, and optionally a lipid panel A visits row — measurements only A risk assessment, scored immediately
Reads the result A risk_assessments row low / medium / high, a 0–100 score, and a confidence flag

A patient is identified by a clinician-chosen reference — a chart label like JD-0412 — not by a legal name. Diacify never stores one ADR-038.

02

Two lifecycles, one file

Diacify has two separate lifecycles. One trains a model; the other serves it. Different languages, different workspaces, different times, no shared code — meeting at exactly one file.

Training

Python · run by hand, rarely

  • 662-row CSV dataset
  • parse & clean each field
  • impute missing values
  • engineer ratios & flags
  • assign ADA 2025 labels
  • leakage-safe train/test split
  • fit random forest · 100 trees
  • cross-validate, audit bias
  • export
They meet here backend/src/ml/model.json

Serving

TypeScript · every prediction

  • load & validate model.json at boot
  • visit measurements arrive
  • build 13-value feature vector
  • walk all 100 trees
  • average into 3 probabilities
  • derive score, category, confidence
  • store the assessment

The serving model
A trained model flattened into plain data — no code, no runtime, nothing to execute. Just the numbers a prediction needs.
In Diacify model.json holds 100 decision trees as nested thresholds, the feature order, the class names ["low","medium","high"], and the imputation medians learned during training. It is committed to git alongside the code that reads it, and stamped with a version — currently rf-098c19d0afc9. The Python side writes it; the Node side only ever reads it ADR-025.

What porting the forest into the backend removed

Legacy DiacifyNow
Inference runs in A separate Python service The backend process
A prediction is A network call A function call
If it's unavailable The visit saves unscored Cannot happen
So the schema needed A 'pending' state on every visit Nothing — no row means not scored

Two runtimes became one ADR-001. Training stayed in Python because scikit-learn, cross-validation and bias-audit tooling live there — and it runs on a laptop, not in production.

03

The map

Four workspaces in one repository, plus one managed platform doing work that would otherwise be code.

frontend/

Eight pages a clinician actually uses — landing, sign in, sign up, patient list, new and edit patient, patient detail, record visit. Fetches from the backend and renders; holds no business rules.

Vite · React Router · TanStack Query
shared/

The request shapes both sides agree on, as Zod schemas. The frontend validates a form against the same object the backend validates the request against, so the two cannot drift.

TypeScript · Zod · npm workspace
backend/

Eight HTTP endpoints across two routers, the authentication and rate-limit gates, and the ML serving code that turns a visit into a risk assessment in-process.

Node · Express · TypeScript
machine-learning/

Fifteen single-purpose modules run top to bottom by train.py: raw CSV in, evaluated model out, plus the audit trail. Never runs in production.

Python · scikit-learn · pytest
Supabase

Not a workspace — a managed platform. Provides identity (Auth), the database (Postgres), and, critically, the authorization rules that decide who can see which rows.

Auth · Postgres · Row-level security
Deployment

The backend runs on Render, the frontend on Vercel, the database is hosted Supabase. Three services, no container orchestration ADR-006.

Render · Vercel · Supabase

Everything except machine-learning/ is TypeScript, and all four workspaces share one root lockfile ADR-041.

04

The domain

Four concepts. Two are easy; two carry a distinction that shapes the database, the API, and the UI.

Clinician
The person using Diacify. Owns everything they create, and can never see anything they didn't.
In Diacify A Supabase Auth user. There is no clinicians table of our own — patients.clinician_id references auth.users(id) directly.
Patient
A person under a clinician's care, identified by a label that clinician chose.
In Diacify A patients row holding a reference (1–40 characters, unique per clinician) and sex — which is here for one reason only: it is the single patient-level attribute the trained model actually consumes ADR-014. Everything else clinical belongs to a visit, not the person.
Visit — a fact
An observation. What was measured, on a given date. True regardless of what anyone concludes from it.
In Diacify A visits row: age, systolic, diastolic, BMI and HbA1c are required; RBS, cholesterol, triglycerides, HDL, LDL and VLDL are nullable, because a clinician doesn't draw a full lipid panel every time. There are no score columns on this table at all ADR-018.
Risk assessment — a judgement
A conclusion drawn from a fact by a particular model at a particular time. Can be revisited; can be wrong; can be superseded.
In Diacify A risk_assessments row referencing a visit, stamped with the model_version that produced it. Append-only: one row per (visit, model_version) pair, so retraining adds a second opinion rather than erasing the first ADR-028.
The distinction that shapes the schema

Facts and judgements are stored separately, on purpose. Legacy Diacify put the measurements and the model's output on the same row, so re-scoring a visit overwrote history and a model_version column could only ever mean "the latest one". Splitting them makes "did the retrain move anyone between categories?" an answerable question instead of an erased one.

Score and category answer different questions

Every assessment carries both a risk_score (0–100) and a risk_category (low / medium / high). It is natural to assume one is derived from the other. It isn't — and the reason is the most instructive thing in the domain.

The model outputs three probabilities that sum to 1. The category is simply whichever is largest. The score is a weighted sum — medium counts half, high counts fully — designed for ranking one patient against another. Move the sliders and watch them disagree.

The model's three probabilities

Low is whatever remains — the three always sum to 1, so it isn't independently adjustable.

risk_category — what is this patient?
low

argmax(low, medium, high)

risk_score — how urgently, versus others?
47.50

(0.5 × medium + 1 × high) × 100

low confidence

Why deriving one from the other breaks

Patient low medium high score category
A 0.45 0.15 0.40 47.50 low
B 0.25 0.60 0.15 45.00 medium

A scores higher than B while being categorised lower. Both are correct.

How both can be true at once

A carries a 40% chance of high risk, so A is worth looking at first — the score doing its job. But the model's single best guess for A is still "low", and B's is "medium" — the category doing its job.

Band the score into categories and you would report A as the higher-risk patient, contradicting the model. That is why Diacify computes them independently.

Low confidence
A signal that the model's top answer wasn't a clear winner, so a clinician shouldn't read the category as settled.
In Diacify Set when the highest of the three probabilities falls below 0.55. The threshold has to sit above 1/3 to mean anything at all — with three classes the top probability can never be lower than that, so an earlier 0.40 threshold was advertised but literally unreachable.
05

The one idea to hold onto

If you remember one thing

The backend does not decide who owns what data. It forwards the clinician's own token to Postgres and lets the database answer. No route handler in Diacify contains a clinician_id filter — not one — and that is not an oversight.

Row-level security (RLS)
A rule attached to a table itself, saying which rows the current user is allowed to touch. The database enforces it on every query, no matter who is asking or what they asked for.
In Diacify Each request builds a Supabase client from the caller's own JWT, so queries run as that clinician ADR-013. A SELECT * FROM patients with no WHERE clause returns only their patients — because Postgres silently adds the condition.

Ownership gets further from the row at each level, so each table proves it by walking back up the chain.

patients Owned directly
clinician_id = auth.uid()

The row names its owner, so the check is one comparison.

visits Owned through one join
exists ( select 1 from patients p where p.id = visits.patient_id and p.clinician_id = auth.uid() )

Nothing on a visit names a clinician, so ownership is proved by looking at its patient ADR-017.

risk_assessments Owned through two joins
exists ( select 1 from visits v join patients p on p.id = v.patient_id where v.id = risk_assessments.visit_id and p.clinician_id = auth.uid() )

Assessment → visit → patient → clinician, resolved in one expression.

Why not just put a clinician_id on every table?

It reads more simply, and it is a common design. It also leaves the write path open. Follow one insert down both routes:

Why the column isn't worth keeping alongside the join

Closing that write hole requires the join check anyway. Once it is there, the denormalized column adds nothing to enforcement — it just becomes a second place ownership is recorded, and therefore a second place it can disagree with itself.

Legacy Diacify checked this precedent: it scoped visits through patients too, and denormalized only onto appointments, a different table with a different reason ADR-017.

What follows from this one decision

  • No route handler mentions a clinician. There is nothing to forget to filter by.
  • Another clinician's patient returns 404, not 403 — invisible rather than forbidden, so the API never confirms someone else's record exists.
  • A bad patient_id surfaces as a Postgres 42501 rather than a clean validation error ADR-008.
06

Check yourself

If Part 1 landed, these should be answerable before you open the answer. If one isn't, the section it came from is worth a second pass.

Q1Someone asks "is Diacify a Python app or a Node app?" Why is that question malformed?

Because it conflates the two lifecycles. Training is Python and runs offline on a laptop, rarely, by hand. Serving is TypeScript and runs in the backend on every prediction. The running application in production contains no Python at all — it reads model.json, which Python produced earlier. The correct answer is "Node in production; Python produced the model it serves."

Q2Why doesn't the visits table have a risk_score column?

A visit is a fact — what was measured. A score is a judgement — what one model concluded about those measurements. Storing them on one row means re-scoring overwrites the previous conclusion, which destroys the ability to compare model versions and makes the stored model_version meaningless. They live in separate tables, and assessments are append-only per (visit, model_version).

Q3Patient A's score is 47.5 and category is low; patient B's score is 45.0 and category is medium. Is that a bug?

No — they answer different questions. The category is the model's single most likely class (argmax). The score is a ranking number weighting medium at half and high at full. A is a genuinely split case carrying 40% probability of high risk, so it ranks above B for attention, while its single best guess is still "low". Deriving the category by banding the score is the actual bug — it would report A as higher-risk than B, contradicting the model.

Q4You're reviewing a new endpoint. It filters by clinician_id in the query. What do you say?

That it shouldn't need to. Queries run through a Supabase client built from the caller's own JWT, so RLS already restricts every statement to that clinician's rows. A hand-written filter is at best redundant, and at worst misleading — it implies the application is the thing enforcing ownership, which invites someone later to write an endpoint that forgets. The database is the enforcement point; the application never gets a vote.

Q5Why does requesting another clinician's patient by id return 404 rather than 403?

Because RLS doesn't hide the row from the response — it hides it from the query. The backend genuinely finds nothing, so "not found" is the honest answer. It's also the safer one: a 403 would confirm that a record with that id exists and belongs to someone else, which is information the caller shouldn't have.
