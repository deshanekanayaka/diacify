Diacify Developer docs

How Diacify works, from the top down

A clinician records what they measured at a patient visit. Diacify answers with a diabetes risk assessment. Everything below explains how that sentence turns into a running system — no prior knowledge of this codebase assumed.

High level The shape of the system and the five ideas you need before any code makes sense. Readable start to finish in about ten minutes. Low level One request traced end to end, the gates, RLS in detail, ML serving, the training pipeline, and the seams.
01

What Diacify is

Diacify is a tool for one kind of person doing one kind of job: a clinician, seeing a patient, who wants to know how that patient's numbers read against a diabetes risk model.

The whole product is three nouns and one verb: a clinician keeps patients, each patient accumulates visits, and recording a visit produces a risk assessment.

No appointments, no analytics dashboard. Both existed in legacy and were deliberately left out ADR-043.

One pass through the product

The clinician doesDiacify recordsThey get back
Signs up, signs in An identity in Supabase Auth A session; everything after this is scoped to them
Adds a patient with a chart reference A patients row: reference, sex A patient in their list — no name, no date of birth
Records a visit: age, blood pressure, BMI, HbA1c, and optionally a lipid panel A visits row — measurements only A risk assessment, scored immediately
Reads the result A risk_assessments row low / medium / high, a 0–100 score, and a confidence flag

A patient is identified by a clinician-chosen reference — a chart label like JD-0412 — not by a legal name. Diacify never stores one ADR-038.

02

Two lifecycles, one file

Diacify has two separate lifecycles. One trains a model; the other serves it. Different languages, different workspaces, different times, no shared code — meeting at exactly one file.

Training

Python · run by hand, rarely

  • 662-row CSV dataset
  • parse & clean each field
  • impute missing values
  • engineer ratios & flags
  • assign ADA 2025 labels
  • leakage-safe train/test split
  • fit random forest · 100 trees
  • cross-validate, audit bias
  • export
They meet here backend/src/ml/model.json

Serving

TypeScript · every prediction

  • load & validate model.json at boot
  • visit measurements arrive
  • build 13-value feature vector
  • walk all 100 trees
  • average into 3 probabilities
  • derive score, category, confidence
  • store the assessment

The serving model
A trained model flattened into plain data — no code, no runtime, nothing to execute. Just the numbers a prediction needs.
In Diacify model.json holds 100 decision trees as nested thresholds, the feature order, the class names ["low","medium","high"], and the imputation medians learned during training. It is committed to git alongside the code that reads it, and stamped with a version — currently rf-098c19d0afc9. The Python side writes it; the Node side only ever reads it ADR-025.

What porting the forest into the backend removed

Legacy DiacifyNow
Inference runs in A separate Python service The backend process
A prediction is A network call A function call
If it's unavailable The visit saves unscored Cannot happen
So the schema needed A 'pending' state on every visit Nothing — no row means not scored

Two runtimes became one ADR-001. Training stayed in Python because scikit-learn, cross-validation and bias-audit tooling live there — and it runs on a laptop, not in production.

The map

Four workspaces in one repository, plus one managed platform doing work that would otherwise be code.

frontend/

Eight pages a clinician actually uses — landing, sign in, sign up, patient list, new and edit patient, patient detail, record visit. Fetches from the backend and renders; holds no business rules.

The request shapes both sides agree on, as Zod schemas. The frontend validates a form against the same object the backend validates the request against, so the two cannot drift.

Eight HTTP endpoints across two routers, the authentication and rate-limit gates, and the ML serving code that turns a visit into a risk assessment in-process.

Node · Express · TypeScript

Fifteen single-purpose modules run top to bottom by train.py: raw CSV in, evaluated model out, plus the audit trail. Never runs in production.

Python · scikit-learn · pytest

Not a workspace — a managed platform. Provides identity (Auth), the database (Postgres), and, critically, the authorization rules that decide who can see which rows.

Auth · Postgres · Row-level security

Render · Vercel · Supabase

04

The domain

Four concepts. Two are easy; two carry a distinction that shapes the database, the API, and the UI.

Clinician
The person using Diacify. Owns everything they create, and can never see anything they didn't.
In Diacify A Supabase Auth user. There is no clinicians table of our own — patients.clinician_id references auth.users(id) directly.
Patient
A person under a clinician's care, identified by a label that clinician chose.
In Diacify A patients row holding a reference (1–40 characters, unique per clinician) and sex — which is here for one reason only: it is the single patient-level attribute the trained model actually consumes ADR-014. Everything else clinical belongs to a visit, not the person.
Visit — a fact
An observation. What was measured, on a given date. True regardless of what anyone concludes from it.
In Diacify A visits row: age, systolic, diastolic, BMI and HbA1c are required; RBS, cholesterol, triglycerides, HDL, LDL and VLDL are nullable, because a clinician doesn't draw a full lipid panel every time. There are no score columns on this table at all ADR-018.
Risk assessment — a judgement
A conclusion drawn from a fact by a particular model at a particular time. Can be revisited; can be wrong; can be superseded.
In Diacify A risk_assessments row referencing a visit, stamped with the model_version that produced it. Append-only: one row per (visit, model_version) pair, so retraining adds a second opinion rather than erasing the first ADR-028.
The distinction that shapes the schema

Facts and judgements are stored separately, on purpose. Legacy Diacify put the measurements and the model's output on the same row, so re-scoring a visit overwrote history and a model_version column could only ever mean "the latest one". Splitting them makes "did the retrain move anyone between categories?" an answerable question instead of an erased one.

Score and category answer different questions

Every assessment carries both a risk_score (0–100) and a risk_category (low / medium / high). It is natural to assume one is derived from the other. It isn't — and the reason is the most instructive thing in the domain.

The model outputs three probabilities that sum to 1. The category is simply whichever is largest. The score is a weighted sum — medium counts half, high counts fully — designed for ranking one patient against another. Move the sliders and watch them disagree.

The model's three probabilities

Low is whatever remains — the three always sum to 1, so it isn't independently adjustable.

risk_category — what is this patient?
low

argmax(low, medium, high)

risk_score — how urgently, versus others?
47.50

(0.5 × medium + 1 × high) × 100

low confidence

Why deriving one from the other breaks

Patient low medium high score category
A 0.45 0.15 0.40 47.50 low
B 0.25 0.60 0.15 45.00 medium

A scores higher than B while being categorised lower. Both are correct.

How both can be true at once

A carries a 40% chance of high risk, so A is worth looking at first — the score doing its job. But the model's single best guess for A is still "low", and B's is "medium" — the category doing its job.

Band the score into categories and you would report A as the higher-risk patient, contradicting the model. That is why Diacify computes them independently.

Low confidence
A signal that the model's top answer wasn't a clear winner, so a clinician shouldn't read the category as settled.
In Diacify Set when the highest of the three probabilities falls below 0.55. The threshold has to sit above 1/3 to mean anything at all — with three classes the top probability can never be lower than that, so an earlier 0.40 threshold was advertised but literally unreachable.
05

The one idea to hold onto

If you remember one thing

The backend does not decide who owns what data. It forwards the clinician's own token to Postgres and lets the database answer. No route handler in Diacify contains a clinician_id filter — not one — and that is not an oversight.

Row-level security (RLS)
A rule attached to a table itself, saying which rows the current user is allowed to touch. The database enforces it on every query, no matter who is asking or what they asked for.
In Diacify Each request builds a Supabase client from the caller's own JWT, so queries run as that clinician ADR-013. A SELECT * FROM patients with no WHERE clause returns only their patients — because Postgres silently adds the condition.

Ownership gets further from the row at each level, so each table proves it by walking back up the chain.

patients Owned directly
clinician_id = auth.uid()

The row names its owner, so the check is one comparison.

visits Owned through one join
exists ( select 1 from patients p where p.id = visits.patient_id and p.clinician_id = auth.uid() )

Nothing on a visit names a clinician, so ownership is proved by looking at its patient ADR-017.

risk_assessments Owned through two joins
exists ( select 1 from visits v join patients p on p.id = v.patient_id where v.id = risk_assessments.visit_id and p.clinician_id = auth.uid() )

Assessment → visit → patient → clinician, resolved in one expression.

Why not just put a clinician_id on every table?

It reads more simply, and it is a common design. It also leaves the write path open. Follow one insert down both routes:

Why the column isn't worth keeping alongside the join

Closing that write hole requires the join check anyway. Once it is there, the denormalized column adds nothing to enforcement — it just becomes a second place ownership is recorded, and therefore a second place it can disagree with itself.

Legacy Diacify checked this precedent: it scoped visits through patients too, and denormalized only onto appointments, a different table with a different reason ADR-017.

What follows from this one decision

  • No route handler mentions a clinician. There is nothing to forget to filter by.
  • Another clinician's patient returns 404, not 403 — invisible rather than forbidden, so the API never confirms someone else's record exists.
  • A bad patient_id surfaces as a Postgres 42501 rather than a clean validation error ADR-008.
06

One request, end to end

Everything in Part 1 shows up in one call. Recording a visit is the only endpoint that touches all four workspaces and both ML lifecycles' meeting point in a single round trip, so it is the one worth tracing in full — real status codes, real function names.

Where each step actually lives

StepFile
Form submitfrontend/src/pages/RecordVisitPage.tsx
Request shape (compile-time only, see below)shared/src/createVisitSchema.ts
requireAuthbackend/src/middleware/requireAuth.ts
rateLimitbackend/src/middleware/rateLimit.ts
Route handler, validation, insertbackend/src/routes/patients.ts
Feature vector → forest → verdictbackend/src/ml/features.ts, forest.ts, riskAssessment.ts
Persist the assessmentbackend/src/db/riskAssessments.ts

The shared schema runs at two different times. createVisitSchema() lives in shared/ so both sides agree on one definition — but the frontend never calls .safeParse() on it, only imports the inferred CreateVisitInput type. The backend is the only place it actually runs, on the real body: one definition, a compile-time contract on one side, a runtime gate on the other.

Why the visit is committed before it's scored

The insert and the scoring are two separate calls, not one transaction. If assessRisk() or the assessment insert fails, the visit — a clinical fact that already happened — stays saved, with risk_assessment: null in the response. POST /api/visits/:id/predict can score it later.

The alternative — one transaction covering both — would roll the visit back if scoring failed for any reason, including a bug in the scoring code that has nothing to do with whether the measurement itself was real ADR-032.

07

The gates

Three checks run before a write ever reaches a route handler's own logic. The order they run in isn't a convention — one of them is a literal data dependency on the one before it.

GateRejects withKeyed by
requireAuth 401 bad/missing token
503 JWKS unreachable		 The Authorization header
rateLimit 429, with Retry-After req.user.id
Zod validation 400 The request body
The ordering is mechanical, not defensive

rateLimit keys its lookup on req.user.id. That field does not exist until requireAuth sets it. Rate limiting is scoped per clinician, so it cannot even ask "how many requests has this caller made" before it knows who the caller is — swapping the two wouldn't just be less safe, it would throw.

Why a timed-out JWKS fetch is 503, not 401

JWKSTimeout extends the same JOSEError base class every bad-token error does, so it would fall into the general 401 branch by default. requireAuth checks for it explicitly, first, and maps it to 503 instead ADR-033.

The distinction matters to the person on the other end: a bad token means "log in again," something a clinician can act on. A verification service being unreachable is an outage they cannot fix by logging in again — telling them to would be actively wrong.

Why rateLimit is in-memory, and what that costs

Each clinician's recent write timestamps live in a Map inside the backend process. Correct for one running instance; a second instance would keep its own, separate count, so a clinician split across two instances by a load balancer effectively gets twice the budget. A shared store (Postgres, Redis) would fix that — not needed yet at Diacify's per-clinic scale, and documented as a real limitation rather than hidden.

08

Data and security, in detail

Part 1 covered who owns a row. This is who is allowed to touch the database at all, and it turns out Diacify answers that question more strictly than most Supabase projects do by default.

Table grants, by role

RoleOn patients / visitsOn risk_assessments
anonNothing — revoked at the role level, including future tables ADR-012Nothing
authenticatedselect, insert, update, deleteselect, insert only — an assessment is never edited or deleted, only added ADR-029
service_roleNothing — revoked entirely ADR-035Nothing

service_role usually means "bypass RLS." Supabase grants it that by default. Diacify revoked its table privileges to zero anyway: nothing currently needs to act across every clinician's rows at once, and a credential that can bypass every check is a bigger attack surface than the convenience is worth while nothing uses it.

Migrations that assert their own end state

Several grant migrations end with a do $$ ... end $$ block that queries Postgres's own catalog and raises an exception if the role still holds a privilege it shouldn't. A future migration that accidentally re-grants something fails immediately, in CI, rather than silently widening access.

select string_agg(...) from pg_class c cross join lateral aclexplode(c.relacl) a where pg_get_userbyid(a.grantee) = 'service_role'; if offending is not null then raise exception 'service_role holds table privileges it should not: %', offending; end if;

The list view's RLS gotcha

patients_with_latest_risk — behind the patient list's server-side risk filter/sort — joins all three tables. A Postgres view runs with its creator's privileges by default, which would silently bypass RLS underneath it.

It's declared with (security_invoker = true), so it runs as the querying clinician instead — one line standing between "this view respects RLS" and "this view is a hole in it" ADR-042.

09

ML serving

model.json is plain data — no code. Loaded once at boot, validated against a Zod schema before the server accepts a single request, per the project rule that a model artifact is untrusted input like any other.

{ "version": "rf-098c19d0afc9", "featureNames": ["hba1c", "age", "sex_encoded", ...], // 13 total "classes": ["low", "medium", "high"], "medians": { "age": ..., "hba1c": ..., ... }, // training-set medians "ratioMedians": { "tg_hdl_ratio": ..., "ldl_hdl_ratio": ... }, "trees": [ { "left": [...], "right": [...], "feature": [...], "threshold": [...], "value": [...] }, ... ] // 100 of these }

13 features, built from a visit and a patient

Nine are read straight off the visit. Four are derived:

  • hypertension_flag — 1 if systolic ≥ 140 mmHg or diastolic ≥ 90 mmHg, else 0.
  • tg_hdl_ratio, ldl_hdl_ratio — triglycerides/HDL and LDL/HDL, or a training-time median ratio when HDL is 0 (can't divide by it).
  • age_bmi_interaction — age × BMI, a single term letting the forest see the two together rather than only separately.

A missing optional lab (RBS, triglycerides, HDL, LDL) is filled with the median from the training set, not zero and not omitted — the same treatment a blank value got when the model learned, so serving and training stay consistent.

Why the code compares Math.fround(value), not the raw number. scikit-learn casts every feature to 32-bit float before comparing it to a threshold; JavaScript numbers are 64-bit. Math.fround reproduces that rounding first, so the Node traversal is bit-exact with the Python model — not approximately equal, exactly equal.

What breaks without it

A value can sit between a threshold and the next representable float32 above it — close enough to be "the same number" at float64 precision, but on the other side of the split once cast to float32. Without rounding first, that value takes the other branch, lands in a different leaf, and can change the predicted category. Confirmed with a real near-threshold case in forest.test.ts, not just reasoned about.

Walking the forest

Each of the 100 trees is walked root to leaf — at every node, compare one feature to a threshold, go left or right. The leaf holds a probability distribution over the three classes.

The forest's answer is the plain average of all 100 leaves — where riskAssessment.ts picks up: score, category, and confidence, exactly as walked through in Part 1.

10

ML training

Fifteen single-purpose Python modules, run top to bottom by train.py, each depending only on the ones above it.

The split happens before imputation, on purpose. Rows split into train/test first, stratified by HbA1c alone (the one field guaranteed present before cleanup) — then imputation medians are fit on training rows only, applied to both splits.

Why fitting medians on the full dataset first would be wrong

It would leak information from the test set into what the model learned — a median computed partly from rows the model is later "tested" against, inflating its apparent accuracy on data it never really saw cold.

The label itself: a two-stage clinical rule, not a model output

This is worth pausing on, because it is not obvious from the module list: the training labels aren't scraped from the dataset, they're computed by a hand-written clinical rule, cited to real guidelines.

Stage A Base label, from HbA1c alone

<5.7% low · 5.7–6.4% medium · ≥6.5% high — the ADA 2025 Standards of Care diagnostic thresholds.

Stage B Upgrade rule, never downgrades

Count five secondary flags — hypertension, obesity (BMI ≥ 30), elevated RBS (≥ 126), high TG/HDL (≥ 2.8), high LDL/HDL (≥ 3.5). Two or more raised: the base label moves up one tier, capped at high.

Four of those five flags are the same ones features.ts builds for the model to read — the labelling rule and the model's own features are drawn from the same clinical reasoning, just used two different ways: one decides what a training row is called, the other is a number the forest learns a weight for.

Evaluation

  • 5-fold stratified cross-validation and a held-out test set, both reported in model_metadata.json alongside the exact thresholds used to produce that run's labels — a retrain's audit trail, not just its accuracy number.
  • bias_audit.py breaks performance down by sex and by age band (under 40 / 40–60 / over 60), checking for a group the model is systematically less reliable for.
11

The seams

Where the design deliberately draws its lines, and what crossing each one would cost.

Parse untrusted data once, at the boundary
Zod schemas sit at the HTTP edge. After .safeParse() succeeds, the rest of the request works with typed data and never re-checks it. .strict() means the accepted field set is explicit — an unexpected field is rejected, not silently dropped.
The ML modules know nothing about the web
assessRisk(model, visit, sex) takes plain values and returns a plain object — no database, no req, no clock. The same function would work unchanged from a batch backfill script. One call hides feature engineering, a 100-tree traversal, a float32 parity subtlety, and three business rules behind three arguments — a deep module, in the sense that matters: the interface is far simpler than what it does.
Authorization lives in Postgres, not in application code
Handlers pass the caller's own token down and let RLS filter. The honest trade-off: this leaks upward in places. Route code still has to know that 42501 means "not your patient," and that a failed read and a failed write surface differently. Real coupling to the database's behaviour — accepted because the alternative, every handler remembering to filter by clinician_id, fails open the moment one of them forgets.
One composition root
server.ts is the only file that reads process.env, reads the filesystem, or constructs anything. Everything else takes its dependencies as arguments — createRequireAuth(getKey), createRateLimiter({ now }). That is why the rate limiter can be tested with a fake clock and no server running at all.

Where it's thinner than it looks

Worth having an opinion on, not just accepting:

  • A new Supabase client is built on every request, for RLS to work correctly — real, deliberate object-construction cost.
  • The rate limiter is per-process — correct for one backend instance, and documented as a limitation rather than solved.
  • No structured logging — a 500 currently leaves a trace only where logInternalError is explicitly called.
  • db/ isn't really a repository layer. Only riskAssessments.ts lives there; patient and visit queries are written inline in the routes that use them once each — defensible, but an asymmetry worth being able to justify.
12

Check yourself

If this landed, these should be answerable before you open the answer. If one isn't, the section it came from is worth a second pass.

Q1Someone asks "is Diacify a Python app or a Node app?" Why is that question malformed?

Because it conflates the two lifecycles. Training is Python and runs offline on a laptop, rarely, by hand. Serving is TypeScript and runs in the backend on every prediction. The running application in production contains no Python at all — it reads model.json, which Python produced earlier. The correct answer is "Node in production; Python produced the model it serves."

Q2Why doesn't the visits table have a risk_score column?

A visit is a fact — what was measured. A score is a judgement — what one model concluded about those measurements. Storing them on one row means re-scoring overwrites the previous conclusion, which destroys the ability to compare model versions and makes the stored model_version meaningless. They live in separate tables, and assessments are append-only per (visit, model_version).

Q3Patient A's score is 47.5 and category is low; patient B's score is 45.0 and category is medium. Is that a bug?

No — they answer different questions. The category is the model's single most likely class (argmax). The score is a ranking number weighting medium at half and high at full. A is a genuinely split case carrying 40% probability of high risk, so it ranks above B for attention, while its single best guess is still "low". Deriving the category by banding the score is the actual bug — it would report A as higher-risk than B, contradicting the model.

Q4You're reviewing a new endpoint. It filters by clinician_id in the query. What do you say?

That it shouldn't need to. Queries run through a Supabase client built from the caller's own JWT, so RLS already restricts every statement to that clinician's rows. A hand-written filter is at best redundant, and at worst misleading — it implies the application is the thing enforcing ownership, which invites someone later to write an endpoint that forgets. The database is the enforcement point; the application never gets a vote.

Q5Why does requesting another clinician's patient by id return 404 rather than 403?

Because RLS doesn't hide the row from the response — it hides it from the query. The backend genuinely finds nothing, so "not found" is the honest answer. It's also the safer one: a 403 would confirm that a record with that id exists and belongs to someone else, which is information the caller shouldn't have.

Q6A clinician reports rate-limit errors on visits they never sent. Where do you look first?

Whether they're being routed to more than one backend instance. The rate limiter keys its count on req.user.id in an in-memory Map, per process — two instances keep two separate counts, which doesn't explain extra rejections on its own, but does mean the limiter's real budget silently depends on how many instances are running. The fix, if it were needed, is a shared store (Postgres or Redis), not a higher limit.

Q7What does Math.fround in forest.ts actually protect against?

scikit-learn compares split thresholds in 32-bit float precision; a plain JavaScript number is 64-bit. A feature value can sit in the gap between a threshold and the nearest float32 above it — close enough to be "the same number" at float64 precision, but on the other side of the split once cast to float32. Without Math.fround first, that value walks a different path through the tree and can land in a different leaf, occasionally changing the predicted category. Confirmed with a real near-threshold case in forest.test.ts, not just reasoned about.

Q8service_role usually bypasses RLS entirely. Why does Diacify hold it to zero table grants?

Because nothing in the running application currently needs to act across every clinician's rows at once — every real operation is scoped to one authenticated clinician already. A credential that can ignore every ownership check is a standing attack surface (a leaked key, a compromised script) proportional to what it can reach, not to what actually uses it. Holding it at zero costs nothing today and removes that surface entirely; it can be widened deliberately, migration by migration, the day something genuinely needs it.
