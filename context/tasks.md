## Now

- [ ] Decide whether a JWKS outage should read as 401 or 503 — `requireAuth`'s catch block intends to split "caller's fault" (401) from "our key service is down" (503), but what it actually branches on is `error instanceof joseErrors.JOSEError`, and `JWKSTimeout extends JOSEError` (confirmed in `node_modules/jose/dist/node/cjs/util/errors.js:102`). So a JWKS fetch that *times out* returns 401 — telling a clinician to log in again during an outage they cannot fix, which is exactly what ADR/the 503 branch exists to prevent — while a JWKS host that *refuses the connection* throws a plain fetch `TypeError` and correctly returns 503. Two infrastructure failures, same root cause, different status codes, and the more likely one gets the wrong answer. The test suite does not catch this: `requireAuth.test.ts:98` proves the 503 path by throwing a plain `Error("network unreachable")`, which `jose` would never produce for a real network failure — a green test guarding a path real conditions may route around. **Decide:** whether to catch `JWKSTimeout` (and possibly `JWKSNoMatchingKey`, which can mean a key rotation we haven't refreshed rather than a bad token) explicitly before the generic JOSE branch and map them to 503, or accept 401 as the answer for all verification failures and delete the 503 branch as unreachable-in-practice. - [ ] Investigate why `service_role` has different table privileges locally and on hosted. **What it is:** Supabase runs every request as one of three Postgres roles — `anon` (not signed in), `authenticated` (a signed-in clinician), and `service_role`, which is server-side code and **bypasses RLS entirely** (`pg_roles.rolbypassrls = true`, confirmed). It is the one credential that can read every clinician's data regardless of policy, which is why the backend never uses it: ADR-013 builds a per-request client from the caller's own JWT so queries run as `authenticated`. The secret key lives only in `backend/.env.test`, used solely to delete test users via the auth admin API — deliberately not in `backend/.env`. **The divergence:** querying `visits` as `service_role` on the local stack fails with `permission denied for table visits`, while the same query on the hosted project succeeds — the two databases grant `service_role` different default privileges when a table is created (local gives it only housekeeping ones, hosted gives it full DML). Cause unconfirmed; most likely different Supabase versions, not anything a migration here did. **Why it matters:** nothing today is affected, since no application or test code uses `service_role` for table access. But an admin script or background job written later would work against production and fail locally with a confusing permissions error. Note the direction too — local is the *more* locked down of the two, so production is the permissive one, which is the wrong way round for a role that bypasses RLS. **Decide:** whether to pin `service_role`'s grants explicitly in a migration so both environments agree (and which way), or leave it and document the difference.
