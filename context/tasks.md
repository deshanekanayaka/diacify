- [ ] Investigate why `service_role` has different table privileges locally and on hosted. **What it is:** Supabase runs every request as one of three Postgres roles — `anon` (not signed in), `authenticated` (a signed-in clinician), and `service_role`, which is server-side code and **bypasses RLS entirely** (`pg_roles.rolbypassrls = true`, confirmed). It is the one credential that can read every clinician's data regardless of policy, which is why the backend never uses it: ADR-013 builds a per-request client from the caller's own JWT so queries run as `authenticated`. The secret key lives only in `backend/.env.test`, used solely to delete test users via the auth admin API — deliberately not in `backend/.env`. **The divergence:** querying `visits` as `service_role` on the local stack fails with `permission denied for table visits`, while the same query on the hosted project succeeds — the two databases grant `service_role` different default privileges when a table is created (local gives it only housekeeping ones, hosted gives it full DML). Cause unconfirmed; most likely different Supabase versions, not anything a migration here did. **Why it matters:** nothing today is affected, since no application or test code uses `service_role` for table access. But an admin script or background job written later would work against production and fail locally with a confusing permissions error. Note the direction too — local is the *more* locked down of the two, so production is the permissive one, which is the wrong way round for a role that bypasses RLS. **Decide:** whether to pin `service_role`'s grants explicitly in a migration so both environments agree (and which way), or leave it and document the difference.
